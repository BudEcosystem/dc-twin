# 18 — Day 0: a fabric from the factory

Draft 0.4, 2026-11-13 (Z7, DSX OS through NVIDIA Config Manager, proposed). **Built** (Z0 to Z4; Z5 for net-configurator's spine template on Cumulus
5.15+; Z6 is NetBox with Ansible, `compat/netbox-ansible`, D79): what the build changed is in
[As built](#as-built). Its decisions are D72 to D79 in [11](11-decisions.md); its open questions
are Q25 to Q29 [below](#open-questions).

Today the twin does day 0 itself. At `up` it renders every real switch's start-up configuration
from the model and applies it, through NVUE on `generic/nvue-frr` ([D56](11-decisions.md#d56--cumulus-is-nvue-emulated-over-what-cumulus-is-built-from-genericnvue-frr))
and through CONFIG_DB on `sonic-vs` ([D55](11-decisions.md#d55--sonic-vs-runs-sonics-bgp-and-gnmi-containers-frr-is-configured-from-config_db)):
hostname, Loopback0, the rack segments' VLANs and gateways, addresses on fabric links, numbered
eBGP, the DHCP relay. The software under test (SUT) finds a fabric that is already up, so the
software that brings a fabric up is never tested.

This chapter specifies a second way for a fabric to start: **as its switches leave the factory**.
The SUT then does day 0: ZTP, the first configuration push, cabling validation and the checks
that the fabric converged. The twin serves the protocols that work needs, configures nothing the
SUT should configure, and judges the result against the design it handed the SUT.

## Scope

| In | Out, for now |
|---|---|
| Ethernet fabrics on a real NOS (`generic/nvue-frr` standing in for Cumulus, `sonic-vs`): the `oob-flat`, `clos-2tier` and `clos-3tier` templates | InfiniBand (UFM's subnet manager) and NVLink (NMX) bring-up ([Q29](#open-questions)) |
| A switch's factory state, its management port's DHCP, and its management interfaces at that lease | Switch firmware: ONIE updates, BIOS, CPLD, ASIC firmware |
| ONIE's discovery and fetch of a NOS image | Running a NOS installer; real Cumulus or SONiC installer images |
| Each NOS's ZTP contract | Behaviour of the ASIC, optics, buffers, QoS and RoCE (their configuration is accepted, see [Fidelity](#fidelity)) |
| The first configuration push: NVUE REST, the `nv` CLI over SSH, SONiC's CLI over SSH, gNMI | Console servers and the serial console (a later phase) |
| LLDP, and cabling validated against the design | Enterprise SONiC features and its management-framework REST API |
| The design handed to the SUT, and convergence judged against it | Day 1 and day 2 tenant configuration (VRFs, VNIs, ports per tenant): already served by D56, D57 and D71 |

## Day 0 on a real site

What the twin has to reproduce, in order. The tooling column names what usually does each step;
none of it is assumed by the twin.

| Step | On the site | Usually done by |
|---|---|---|
| 1. Design | Racks, cabling plan, address plan, AS numbers, roles | NetBox or Nautobot, generated from the design |
| 2. Rack and cable | Switches racked, cables run, management ports on the OOB network | People |
| 3. Power on, NOS install | A switch with no NOS boots ONIE, which finds an installer by DHCP and HTTP and installs it. Most Spectrum switches arrive with Cumulus or SONiC already installed | ONIE, a file server |
| 4. ZTP | The NOS's first boot does DHCP on its management port, fetches a script or a ZTP document the DHCP options point to, and runs it | A DHCP server with ZTP options, an HTTP server, per-switch scripts |
| 5. First push | Hostname, users, NTP and DNS, management VRF, breakouts and MTU, loopbacks, underlay BGP (often unnumbered), EVPN, the DHCP relay, QoS for RoCE | Ansible (`nvidia.nvue` over NVUE REST, SSH and `nv`), gNMI, SONiC's `config load`, or a fabric controller |
| 6. Validate | LLDP neighbours against the cabling plan, BGP sessions up, loopbacks reachable, relay working | The same tooling, NetQ, a script |
| 7. Hand over | The fabric is ready for day 1 (host ingest) | |

## Principles

1. **The twin configures nothing the SUT is meant to configure.** A fabric in factory mode
   gets its NOS's factory state and nothing else. Every hostname, address and BGP session it
   ends up with came from the SUT.
2. **Factory state is the NOS's own**, as shipped, read from the NOS's source and documentation
   with a date ([Factory state](#factory-state)). The twin does not guess at what a fresh switch
   looks like.
3. **The protocols are real; installing is modelled.** DHCP, HTTP, SSH, NVUE, gNMI and LLDP are
   the real thing, spoken by real clients where they exist. Writing a NOS image to a switch's
   disk is not, and is labelled ([D75](11-decisions.md#d75--onie-is-modelled-discovery-and-fetch-are-real-the-image-is-recognised-not-run)).
4. **The design is an input and the oracle.** The SUT is handed the design as a site hands it
   ([What the SUT is given](#what-the-sut-is-given)). The plan the twin would have applied itself
   is what the SUT's result is compared with ([D77](11-decisions.md#d77--the-design-is-handed-to-the-day-0-tool-as-a-site-hands-it-and-is-the-oracle)).
5. **Every step leaves an event.** Each DHCP lease and the options served, each ZTP fetch and run,
   each NVUE revision, CONFIG_DB write and CLI command is a committed event with the SUT as
   principal, as NVUE writes already are (D71, I-07). The critic judges from these alone
   ([D64](11-decisions.md#d64--the-critic-judges-only-from-the-event-log-the-model-and-declared-accessors)).
6. **Day 0 can be repeated.** A switch can be returned to factory state without a new estate, so
   a tool's second run (idempotence, recovery from a half-done day 0) is testable.

## The estate

A fabric says how its switches start ([D72](11-decisions.md#d72--a-fabric-may-come-up-in-factory-state-the-twin-then-configures-nothing-a-day-0-tool-would)):

```yaml
fabrics:
  - name: oob
    template: oob-flat
    nos: none                      # model OOB switches: the twin relay serves the management network
  - name: frontend
    template: clos-2tier
    nos: generic/nvue-frr
    params: { leafsPerRack: 2, spines: 2, underlay: unnumbered, overlay: evpn }
    bringUp: factory               # D twin: today's behaviour
    factory:
      install: preinstalled        # or onie: the switch has no NOS until ONIE installs one
      ztp: enabled                 # the NOS's ZTP runs at first boot (disabled: the SUT pushes over SSH or the API)
      plan: given                  # the SUT is handed the address plan; tool: it allocates its own
      bootTime: 90s                # how long a NOS takes from power-on to its management port's DHCP
      installTime: 5m              # ONIE's install, when install is onie
```

| Field | Values | Rules |
|---|---|---|
| `fabric.bringUp` | `twin` (D) \| `factory` | `factory` needs a real `nos` and `spec.adapters.network.substrate: tap` |
| `fabric.factory.install` | `preinstalled` (D) \| `onie` | `onie` needs `spec.adapters.network.nos.images` ([ONIE](#onie)) |
| `fabric.factory.ztp` | `enabled` (D) \| `disabled` | |
| `fabric.factory.plan` | `given` (D) \| `tool` | With `tool`, the oracle checks structure, not values ([Converged](#converged)) |
| `fabric.factory.bootTime`, `installTime` | durations | Shortened under `spec.timeScale`; real switches take minutes |
| `fabric.factory.select` | selector | Only these switches start in factory state; the others are configured by the twin as today. Lets a run start with the spines up and the leaves fresh |

The first integration is expected to keep the OOB fabric at `nos: none`, so the management
network the switches do ZTP on is the twin relay's, with option 82, as for BMCs today. An
`oob-flat` fabric may itself be `factory`; its switches' management ports are then on the service
zone's segment and are leased without a relay, as the first switches on a site are leased from
a management router.

## Factory state

What each NOS has before anything configures it, read on 2026-11-11 (Q25, Q26: the sources are in
[the day-0 vendor facts](../reviews/2026-11-11-day0-vendor-facts.md), sections B and E, and the
pinned docker-sonic-vs image itself).

| | `generic/nvue-frr` (as Cumulus Linux 5.x) | `sonic-vs` |
|---|---|---|
| Hostname | `cumulus` (the factory startup.yaml sets it, so DHCP's host name is not taken) | `sonic` |
| Management port | `eth0`, DHCPv4, in VRF `mgmt` (on by default) | `eth0`, a DHCP client: the twin's (`dctwin-day0 dhcp`), the image has no dhclient |
| Front-panel ports | `swp<n>`, admin down, in no bridge | The HWSKU's port table, up, no addresses |
| Routing | FRR running with no BGP | The bgp container running with no `BGP_*` tables |
| Users | `cumulus`/`cumulus`, expired (a change is forced at the first login, through PAM); root locked | `admin`/`YourPaSsWoRd` (sonic-buildimage's default); the VS image has no `admin`, so the twin adds it, root-equivalent, as it has no sudo |
| Management APIs | SSH; NVUE REST on 8765 at every address (5.14's default with no `listening-address`) | SSH; gNMI as the image ships it |
| ZTP | Runs at first boot when `factory.ztp` is enabled: the twin's client after Cumulus's contract (D74) | The image is built without sonic-ztp (`ENABLE_ZTP` off): the twin's client after sonic-ztp's contract |
| LLDP | `lldpd` (tx-interval 30, hold 4: TTL 120, port ID the interface name) | SONiC's `lldp` container, from the pinned build, beside the switch |

`dctwin switch reset <path> --factory` (and `POST /v1/devices/{path}:factory-reset`) wipes a
switch's configuration and returns it to this state, its ZTP armed again, as `ztp -R` does on
Cumulus. With `install: onie`, `--uninstall` also removes the NOS, as `onie-select -u` does.

## The management port

[D73](11-decisions.md#d73--a-real-switchs-management-port-is-a-dhcp-client-its-management-interfaces-answer-at-that-lease).
Today a real switch's management interfaces answer only in band, at Loopback0 across the fabric,
because the twin configured the loopback. In factory mode there is no loopback until the SUT makes
one, so the management port has to work as on a site:

- A switch's `eth0` is cabled to its rack's management switch by `oob-flat` (the model already has
  the port). The twin moves a TAP with the port's MAC into the switch's namespace as `eth0`
  (D45).
- **The NOS's own DHCP client** runs on it, while the switch is powered on, in VRF `mgmt`. It asks
  for what the NOS asks for (on Cumulus, option 239 among them). Its lease is a `state` event on
  the port's path, in D46's form.
- **SSH (22), NVUE (8765) and gNMI (8080) answer at that lease**, in VRF `mgmt`, reached by the
  SUT through the site gateway as BMCs are. Loopback access keeps working once the SUT has
  configured a loopback, because that is now the SUT's configuration.
- The switch keeps its lease across the SUT's configuration as long as the SUT keeps `eth0` a DHCP
  client in VRF `mgmt`. A SUT that breaks this locks itself out, as on a site, and the critic
  records it ([Judging](#judging)).

## ONIE

[D75](11-decisions.md#d75--onie-is-modelled-discovery-and-fetch-are-real-the-image-is-recognised-not-run).
With `install: onie`, a powered-on switch with no NOS runs a stand-in for ONIE's install
environment (`dctwin-onie`, a small image of its own) on `eth0`:

1. **Discovery** follows ONIE's waterfall: DHCP with ONIE's vendor class (`onie_vendor:<platform>`)
   and its requested options (114 `default-url`, 72 `www-server`, 66/67 TFTP), then the waterfall
   of installer names on the HTTP server (`onie-installer-<arch>-<vendor>_<machine>-r<rev>`, then
   shorter names down to `onie-installer`), then the `onie-server` DNS name. The platform string
   comes from the switch's profile (Q26 checks the Spectrum ones).
2. **The fetch** is a real HTTP GET with ONIE's request headers (serial number, base MAC, vendor
   id, machine, architecture, operation) from the model's identity.
3. **The install is not run.** The twin reads the fetched file's size and sha256 and matches it
   against `spec.adapters.network.nos.images`, a list of `{match: {sha256 | name}, nos}` entries.
   A match "installs" that NOS: after `installTime` the switch reboots into the registry's
   container for it, in factory state. A file that matches nothing, or is for another
   architecture, fails as an ONIE install fails, and ONIE goes back to discovery. Each step is an
   event (`onie.discover`, `onie.fetch`, `onie.install`) with the reason when one fails.

The twin never ships NOS images. A stack serves its own installers, or a placeholder file named
in `images` so the protocol can be exercised without one; the fidelity report says which.

## ZTP

[D74](11-decisions.md#d74--ztp-is-the-noss-own-client-where-its-image-carries-one-otherwise-the-twins-after-the-noss-documented-contract).
Where the NOS image carries its own ZTP client, it runs. Where it does not, the twin's client runs
in the switch's container, implementing that NOS's documented contract, and the fidelity report
labels it.

**Cumulus contract** (`generic/nvue-frr`; to be read again at Z0):

| | |
|---|---|
| Sources, in order | A USB drive (not modelled), then the URL in DHCP option 239 on `eth0` |
| The script | Fetched over HTTP or HTTPS with Cumulus's identifying request headers (architecture, build, manufacturer, product, serial, base and management MACs, version) taken from the model. It must contain `CUMULUS-AUTOPROVISIONING`, or it is refused unrun. It runs as root in the switch |
| Outcome | Exit 0 is success, and ZTP disables itself; anything else is a failure, logged, and ZTP retries as Cumulus's does |
| Control | `ztp -s` (status), `ztp -r <url>` (run now), `ztp -R` (reset) |
| What a script may do | Call `nv` ([D76](11-decisions.md#d76--genericnvue-frr-gains-ssh-and-an-nv-cli-over-the-same-emulated-tree)), write `/etc/network/interfaces` and `/etc/frr/frr.conf` and run `ifreload -a` and FRR's reload (both real), fetch files from the site's servers, install SSH keys and users. NCLU (`net …`) is refused by name; `apt` reaches only what the site's own mirror serves |

**SONiC contract** (`sonic-vs`):

| | |
|---|---|
| Sources | DHCP option 67, the URL of a ZTP JSON document; or option 239, a provisioning script run directly |
| The document | Its sections run in order of their keys, each with `ignore-result`, `halt-on-failure` and `reboot-on-success` honoured. `configdb-json` (fetch a `config_db.json` and load it as `config reload` does), `provisioning-script` and `connectivity-check` are run. `firmware` is the ONIE path above (recognised, not run). `snmp` is applied to CONFIG_DB. `graphservice` (minigraph) is refused by name |
| Status | `ztp status`, as SONiC prints it, from the twin's client when it runs |

What `config reload` does in a container without systemd is Q27. Until it is settled, the twin
reloads a `sonic-vs` switch by restarting its containers on the new CONFIG_DB, and the fidelity
report says so.

## The first push

The surfaces a day-0 tool configures a switch through. Most exist in band today; factory mode
adds them at the management lease, and adds the ones that are missing.

| Surface | NOS | Today | Added here |
|---|---|---|---|
| NVUE REST (`nvidia.nvue` Ansible's path) | `generic/nvue-frr` | At Loopback0, user `cumulus` with a password from `stack-inputs` | At the management lease, with factory credentials and forced change; `system api` listening-address semantics as Cumulus has them |
| `nv` CLI over SSH | `generic/nvue-frr` | Not built | OpenSSH in the image. The twin's `nv`: `set`, `unset`, `show` (a table by default; `-o json`, `-o yaml`), `config apply` (with `-y`), `config diff`, `config replace`, `config save`, `config history`, `config patch`, all on the same NVUE tree as REST (D76) |
| NVUE schema for day 0 | `generic/nvue-frr` | Hostname, interfaces, the one bridge, VNIs, VRFs, BGP (numbered, and since D71 unnumbered with peer groups), EVPN, relay, ACLs, route policy | `system` (timezone, users and AAA, the API's listening address, SSH), `service` (NTP, DNS, syslog, SNMP, LLDP, DHCP relay per VRF), `vrf mgmt`, interface `link` (breakout, MTU, speed, state), `qos roce` (accepted and reported, nothing behind it). Anything else is still refused by name |
| SONiC CLI over SSH (`config`, `show`, `config load`, `config reload`, `config save`) | `sonic-vs` | Reached with `docker exec` by the twin only | sshd in the switch container, factory credentials; `config reload` per Q27 |
| gNMI | `sonic-vs` | At Loopback0; CONFIG_DB through YANG models; native CONFIG_DB writes fail (D-Bus) | At the management lease |

A tool that pushes over SSH or the API without ZTP sets `factory.ztp: disabled`. The switch then
waits in factory state with only its management lease, as a switch with ZTP turned off does.

## LLDP and cabling

[D78](11-decisions.md#d78--lldp-is-real-on-real-noses-and-the-twin-speaks-it-for-model-endpoints).

- **Real NOSes run their own LLDP.** `lldpd` in `generic/nvue-frr` (as Cumulus runs it; `nv show
  interface <swp> lldp` reads it), and SONiC's `lldp` container as a sidecar beside `sonic-vs`
  (pinned with the bgp and gnmi containers, D55; Q25).
- **The twin speaks LLDP for model endpoints** on their TAPs, only while they are powered on:
  model hosts, BMC ports and model switches. Chassis ID is the device's MAC, port ID the port's
  name as the device names it, system name its hostname, every 30 s with a TTL of 120 s. A `vm`
  host's guest speaks for itself if its OS runs an LLDP agent; the twin's guest (`os: twin`) gains
  one.
- **The cabling plan is in the design files** ([What the SUT is given](#what-the-sut-is-given)),
  including a `topology.dot` in the form Cumulus's PTM reads. Whether `ptmd` is in the image is
  Q26.
- **As-built may differ from the design.** A fault catalogue, `generic/cabling`, changes the
  as-built cabling while the design handed to the SUT stays the same: `cable.swap` (two cables'
  far ends exchanged), `cable.wrong-port`, `cable.missing`, `cable.dead` (no carrier),
  `cable.flap`, and `cable.speed-mismatch` (no link until the breakout is set right). The model
  holds both, and the console shows both.

## What the SUT is given

[D77](11-decisions.md#d77--the-design-is-handed-to-the-day-0-tool-as-a-site-hands-it-and-is-the-oracle).
Written to `stack-inputs/day0/` at `up`, beside `expected-machines.json`:

| File | Holds |
|---|---|
| `expected-switches.json` | One entry per switch: path, design hostname, role (`oob`, `leaf`, `spine`, `super-spine`), rack and U, profile and model, ONIE platform string, serial, base MAC, `eth0` MAC, expected NOS |
| `cabling.csv`, `topology.dot` | The design's cables: both ends' device and port names, speed, breakout |
| `plan.json` (with `plan: given`) | The address plan the twin would have applied: loopbacks, router ids, AS numbers, fabric links (`/31`s or unnumbered), management subnet, segment VLANs and gateways, relay targets, the overlay |
| `netbox/` | The same design as NetBox's bulk-import CSVs (sites, racks, device types, devices, interfaces, cables, prefixes, IP addresses, ASNs), so a NetBox the stack runs can be loaded. The NetBox version the CSVs are written for is pinned in the stack definition |

With `plan: tool`, `plan.json` is left out. The SUT allocates its own addresses and AS numbers,
from NetBox or wherever it keeps them.

## Converged

The twin's compiled plan for a switch, the same `nos.Switch` the twin applies itself today, is the
expected outcome. A switch is **converged** when the NOS observer reads, from the switch itself:

- its hostname is the design's hostname for its serial;
- every design fabric link has an established BGP session of the design's kind (numbered or
  unnumbered), with EVPN where the design has an overlay;
- every design loopback is in its RIB;
- each segment it serves has its VLAN and gateway, and its relay forwards (exercised by the
  twin's own endpoints: a model BMC on the segment leases through it);
- its management port still holds its lease, in VRF `mgmt`.

With `plan: tool` the comparison is structural: unique loopbacks and AS numbers per the design's
scheme, a session on every design link, every loopback reachable from every switch.

Each switch moves through `factory → onie-installing → nos-booted → ztp-running → ztp-done |
ztp-failed → configured → converged`. Each transition is an `observer` event.
`dctwin fabric status` and the console's topology view show each switch's phase and its
difference from the design.

## Judging

Day 0 is judged by the critic ([17](17-critic.md)) with a policy shipped as `policies/day0/fabric.yaml`.
It applies when a fabric is in factory mode and is disabled by name otherwise (D67).

| Rule | Form | Dimension |
|---|---|---|
| Every switch powered on reaches `converged` within the stack's objective (default 30 min) | `leadsTo` (**key**) | liveness |
| No switch is given another switch's identity (the hostname, loopback or AS number the design assigns to a different serial) | `never` (**key**) | safety |
| No BGP session is brought up over a link whose as-built far end differs from the design, unless the SUT reported the miscabling first (accessor `alerts`) | `never` (**key**) | safety |
| No switch loses its management lease after the SUT's first write to it | `always` (**key**) | safety |
| At most N reboots of a switch during day 0 | `atMost` | restraint |
| No switch left with factory credentials once converged | `never` | hygiene |
| Cabling was checked: the SUT read LLDP neighbours (an NVUE, CLI or gNMI read of LLDP state) before converging | `sometimes` | coverage |

Measures: time from power-on to first DHCP, to ZTP fetch, to ZTP done and to converged, per
switch and for the fabric (median and maximum); configuration applies per switch, and failed ones;
ZTP retries; requests refused by name (a schema gap on the twin's side, reported against the twin,
not the SUT).

## Faults during day 0

A catalogue `generic/day0`, beside `generic/cabling`:

| Fault | Effect |
|---|---|
| `ztp.server-unreachable` | The URL in the DHCP option does not answer |
| `ztp.script-error` | The script or document returns 404 or 500, or is truncated |
| `ztp.dhcp-no-option` | The lease comes without the ZTP option (a misconfigured scope) |
| `onie.image-mismatch` | The fetched installer is for another platform or fails its checksum |
| `onie.install-power-loss` | Power is lost during `installTime`; the switch comes back to ONIE |
| `switch.doa` | The switch never powers on |
| `switch.slow-boot` | `bootTime` multiplied for this switch |
| `mgmt.duplicate-ip` | Another device answers ARP for the switch's management lease |
| `ntp.unreachable` | The site's NTP does not answer, so clocks drift and certificates may not validate |

Each fault states the reaction the SUT's playbook is expected to have, in the form of [17](17-critic.md#the-playbook).

## Fidelity

What a passing day 0 on the twin does not show, printed in the fidelity report for a factory
fabric:

- That a real installer works: ONIE's discovery and fetch are real, the install is recognised and
  modelled ([D75](11-decisions.md#d75--onie-is-modelled-discovery-and-fetch-are-real-the-image-is-recognised-not-run)).
- That Cumulus Linux behaves this way: `generic/nvue-frr` is what Cumulus is built from, with NVUE,
  `nv` and ZTP emulated after Cumulus's documentation (D56, D74, D76).
- Anything about the ASIC: forwarding is the kernel's; `qos roce`, buffers, PFC and ECN are
  accepted and do nothing.
- Optics and their faults beyond carrier.
- Boot and install times: they are `bootTime` and `installTime`, not measured.
- Switch firmware, licensing, and Enterprise SONiC.

(`scripts/linux-substrate-e2e.sh`, `RUN=TestDay0…`; the results are in
[implementation.md](../implementation.md#day-0)).

**Where it differs from the sections above**, each because a real tool or kernel made it:

- **dhclient runs on `eth0` itself in VRF `mgmt`.** ifupdown2 starts a VRF slave's dhclient under
  `ip vrf exec`, which needs a cgroup a container cannot make; NVUE renders `eth0` with a
  `post-up` that starts dhclient directly (its exchange is its raw socket's), guarded by its pid file.
- **Kea has no `default-url`.** Option 114 is RFC 8910's captive portal now, `v4-captive-portal` to
  Kea 2.6; ONIE reads it as before. Cumulus's 239 needs an `option-def`.
- **BGP runs once an AS is set.** Cumulus configures BGP with `nv set router bgp
  autonomous-system`; the emulated NVUE no longer waits for `router bgp enable on`.
- **A leaf has its own AS by its place in the Clos**, not only when it carries a VLAN, so a
  fabric with no `vm` hosts on it is still eBGP between tiers (RFC 7938).
- **The oracle** judges only factory switches, needs the loopbacks of its own fabric, and not
  those of another switch of its own AS it has no session with (the spines: eBGP's loop check).
- **The twin's bridges forward LLDP** (`group_fwd_mask` bit 14): a cable carries what a cable does.
- **Model BMCs speak LLDP only in an estate with a factory fabric.** In a twin-configured
  `sonic-vs` estate (`TestSonicVS`), the BMCs' frames into the switch's ports were followed by
  SONiC's `dhcprelayd` exiting and the relay container stopping, reproducibly; without them the
  suite is as on `main`. The cause inside SONiC is not known.
- **Observers read factory switches without exec**: their files through `/proc/<pid>/root`, FRR
  over its daemons' vty sockets, SONiC's CONFIG_DB over its redis socket, `/run` paths first
  (a container's `/var/run` is an absolute link, which resolves on the host there); LLDP is the one
  exec, once a minute. Every exec is a session a rootless Podman store keeps and cleans up
  through one database: an observer that exec'd every few seconds piled them up by the thousand
  on a loaded host. The day-0 observer reads every 10 s, the NOS observer BGP every 10 s.
- **Kea reads option 77 as RFC 3004's classes**; SONiC's dhclient sends the bare string
  (`send user-class "SONiC-ZTP"`), so a class matches it by its raw bytes.
- **A factory SONiC switch's bgp container is ready when FRR answers**, not when it holds the
  design's BGP, which only day 0 gives it.
- **`dctwin switch reset <path> --factory`** (`POST /v1/switch/factory-reset`) returns a factory
  switch to its NOS's factory state: NVUE's factory tree over an empty configuration (BGP removed
  with FRR's own `no router bgp`, as frr-reload cannot), or SONiC's factory `config_db.json`
  reloaded; the factory login back and expired; ZTP armed again and run. `--uninstall` (`{"uninstall": true}`) returns a switch ONIE
  installed to ONIE as well. The NOS is reset to its factory configuration and ONIE's
  discovery fetches, matches and installs its image again. After the install, the NOS's
  management DHCP client is restarted, as its boot would start it: ONIE's install releases its
  lease and flushes `eth0`. Only then is ZTP armed. The install stays modelled (D75): the NOS's
  processes keep running meanwhile. The uninstall is modelled for `generic/nvue-frr` only; a
  preinstalled switch's, or a SONiC switch's, is refused by name.

## DSX OS: NVIDIA Config Manager's ZTP

[D80](11-decisions.md#d80--dsx-oss-switch-day-0-is-nvidia-config-managers-contract-run-unmodified).
Draft, 2026-11-13. **Built: Z7a to Z7c** ([As built](#as-built-z7a-2026-11-13), [Z7b and Z7c](#as-built-z7b-and-z7c-2026-11-13)), and Z7d's relay path ([As built: Z7d](#as-built-z7d-2026-11-13)): every BMC leases through the relays NVCM renders, from a stand-in for NICo's DHCP. NICo's own DHCP server in its place, and Z7d's DPU half, are not built.

**Why.** On a DSX OS site, NICo does not configure switches ([nvidia-dsx-os](../stacks/nvidia-dsx-os.md),
*Switches (site-configured)*). The README of NICo at `02b92f1` says so, and its prerequisites ask
for the fabric first:
- a DHCP relay to NICo's DHCP on every BMC-facing network, on the OOB switches;
- eBGP unnumbered from the DPU-facing leaves, with a 32-bit AS per DPU and filters that accept
  loopbacks only;
- EVPN, and a default route into the tenant overlay.

The tool DSX's organisation publishes for that is NVIDIA Config Manager (NVCM,
`dsx-ai-factory/nv-config-manager`, Apache-2.0, a Developer Preview). A Foundry, or any other
day-0 tool, that integrates with DSX OS has to bring switches up the way NVCM does, or drive
NVCM itself. The Metal3 path is already tested on the twin. This is the DSX one.

**What NVCM asks of a site**, read at release 1.4.1 (`2f8bf14`, 2026-10-30):

**How close the twin is.** A probe run all 24 goldens through the emulated NVUE at their own
releases, and the refusals came to about 45 distinct schema paths:

The probe also found that NVCM's 5.16.1 configurations write `enable: on` (EVPN, BGP, NVE, VRR,
a VRF's address families). The twin refuses that on 5.15+, after NVIDIA's *New and Changed NVUE
Commands, 5.15*. Two NVIDIA sources disagree with that refusal: NVCM's goldens, and the
`startup.yaml` on Cumulus 5.16's own EVPN multihoming page, which writes `evpn: enable: on`
beside the CLI's `nv set evpn multihoming state enabled`. Read together, 5.15 changed the CLI's
words while a file or REST tree may still carry `enable`. Until a real 5.15+ switch says
otherwise (Q30), a tree (a `startup.yaml`, a REST PATCH) takes either spelling in every release and the switch holds it in its own, and the CLI
refuses it as before.

On the switch side, beyond the schema, the twin lacks:
- `/etc/os-release` with Cumulus's `VERSION_ID`;
- `nv show platform` and `nv action fetch`;
- `/usr/cumulus/bin/onie-install`;
- `curl` with SFTP (Debian's has it).

**Read further, building Z7a (2026-11-13)**:
- **NVCM's own bug.** Its 5.16.1 configurations put an SVI's VRR at `interface <svi> vrr`. Its
  5.14.0 ones put it at `ip vrr`. NVIDIA's 5.15 change list moves it to `ipv4 vrr`, and nothing
  NVIDIA publishes has the place NVCM uses. Six of the eight 5.16.1 goldens are refused for it,
  as NVCM's gap, so the DSX day-0 estate runs NVCM's 5.14.0 templates. NVCM's 5.16.1 templates
  also write a VRF's loopback as `ip` for one role and `ipv4` for another, so both are taken.
- **eth0's VRF is `mgmt` unless a tree says otherwise.** NVCM's configurations never set
  `interface eth0 ip vrf`, and they put the management default route in `vrf mgmt`. On Cumulus,
  NVUE's eth0 defaults into the management VRF, and the twin renders an eth0 that names no VRF
  there.
- **A ZTP script runs in VRF `mgmt`.** Cumulus starts ZTP from eth0's DHCP hook, and that
  dhclient runs in `mgmt`, so the script inherits it. That is why NVCM's bare `curl`s to
  `validate_serial` and `provisioned` reach it. A container cannot `ip vrf exec`, which needs a
  cgroup and a BPF program. The image instead gains a socket-binding preload (`SO_BINDTODEVICE`
  on each new socket) behind the day-0 programs' `ip vrf exec`. ZTP runs a DHCP-sourced script
  through it, and a script's own `ip vrf exec mgmt` works the same way. Both are UNCONFIRMED as
  Cumulus's mechanism and rest on its documented DHCP hook.
- **The renderer's gaps behind the schema**, each in `nvcm_test.go`'s `renderGaps` until closed:
  - VRR's automatic MAC (`mac-address` unset: Cumulus's `00:00:5E:00:01:<fabric-id>`, or
    `system global fabric-mac`);
  - relays in VRFs other than the default, as server groups, one `dhcrelay` per VRF through the
    same preload;
  - bonds (ifupdown2's `bond-slaves`) with their EVPN multihoming segments (FRR's `evpn mh es-*`);
  - the per-VRF loopback, `evpn multihoming` uplinks and timers, `evpn route-advertise`, and the
    control-plane ACL, which render to nothing today and must not.

### Z7d, scoped (2026-11-13): NICo leases the BMCs through NVCM's relays

**Scope: the BMC half only.** NVCM 1.4.1 cannot do the other half. Its templates render BGP
neighbours only from `bgp_peerings` with a peer address (`role_common/include/vrf.j2`): one
numbered neighbour per fabric link, plus an EVPN peer. No template, golden or filter configures
a leaf port toward a host or DPU for the unnumbered eBGP NICo's prerequisites ask for. "A DPU's
HBN establishes BGP with its leaf" is therefore NVCM's gap, recorded here and in the fidelity
report, and not built. A site's own NVCM template plugin could render those peers, but then NVCM
is no longer run unmodified.

**How NVCM renders an OOB leaf's relay**, read at 1.4.1 (templates `cumulus-linux/oob-leaf`,
which extends `leaf-common` and `superpod-common`; filters `filters/device.py`):
- **Downstream.** `helper_addresses_by_vrf` (`device.py:627`) groups the device's `vlan<N>` SVIs
  by VRF. A VLAN's helpers come from the `vlan_to_helper_address` relationship (VLAN to
  IPAddress), matched by VID alone across all of Nautobot. Only VLANs 201 and 202 get a
  downstream interface (`leaf-common/5.14.0/include/service.j2:11`, a literal).
- **Upstream.** The relay's upstream is `vlan<l3_vlan_id>_l3`, the VRF's L3 VNI SVI. A relayed
  request therefore leaves in VRF `OOB` over EVPN type-5 routes, and its answer returns the same
  way. The leaf's default VRF carries only the underlay.
- **What it needs per leaf:**
  - VRF `OOB` with RD `*:<L3 VNI>` and an `lo-oob` /32;
  - an L3 VXLAN (`l3_vlan_id`, the VRF), and an L2 VXLAN for VLAN 201;
  - `vlan201` in `OOB`, with an address that is not its subnet's first (VRR takes `.1`);
  - BMC-facing ports with untagged VLAN 201;
  - an EVPN peer at a loopback (peer group `EVPN`, multihop, `update-source lo`).
  The blueprint format carries all of it except the helper relationship, which goes in over
  Nautobot's API, as the `UNDERLAY` peer groups already do.
- **NICo's side.** Its `DiscoverDhcp` takes option 82's link selection when present, else the
  relay's `giaddr` (`api-core/src/dhcp/discover.rs:563`). NVCM's relay adds no option 82, so
  NICo picks a BMC's segment by the leaf's `vlan201` address. That address is inside the rack's
  OOB network, which the twin already hands NICo as a segment (`dhcp.PlanSegments`).

**The estate:**
- The OOB fabric's rack management switches start in factory state and are NVCM's OOB-Leafs.
- Their own management ports are cabled to the OOB aggregation switch. That switch is configured
  by the twin, and is the "directly attached" switch NVCM's chain starts from, so their `eth0`
  leases from NVCM's Kea through it.
- The servers' BMCs are cabled to the leaves, as today.
- The aggregation switch is in NVCM's Nautobot as a device NVCM does not provision. It is the
  leaves' underlay and EVPN peer.
- The aggregation switch also holds VRF `OOB` (L3 VNI 2000 on VLAN 4002), with NICo's DHCP server
  on a port in it. It exports that network over EVPN, and the leaves' BMC subnets come back to it
  the same way. The test configures this through the switch's NVUE, as the person who set up the
  first switch would.

**Exit:** every BMC holds a NICo lease from its rack's segment. The lease went through the
relay NVCM rendered on its factory leaf, and NICo recorded the relay's address. The critic's
`day0/fabric` policy passes.

  the `startup.yaml` on Cumulus 5.16's EVPN multihoming page still write `enable: on`. Does a
  5.15+ switch take `enable` in a `startup.yaml` or a REST PATCH, and does it list the factory
  `cumulus` user under `nv show system aaa user`? Until it is read on a real switch (Cumulus VX
  or NVIDIA Air), the twin takes either spelling in trees and holds its release's; the CLI refuses the other release's by name. *Z7a.*
- **Q31 — A lease released by the tool.** NVCM's boot script runs `dhclient -r` and then
  `ifreload -fa`, so the switch has no management address for a moment and comes back with its
  reservation's. The critic's rule "no switch loses its management lease after the SUT's first
  write" would count that as a loss. The proposal: a release followed by the same address within
  the DHCP client's retry window is not a loss; a different address, or none after the window,
  is. *Z7c.*
