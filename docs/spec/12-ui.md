# 12 — UI

A web console for the twin, for seeing the datacenter, changing it, breaking it, and watching
what the software under test does about it.

> **Try it:** [`prototype/`](../../prototype/README.md) is a clickable prototype of this console.
> It runs in the browser over an in-memory estate and a *simulated* stack, with no backend.

## What it is for

| Job | Example |
|---|---|
| **See the estate** | A hall's floor plan with health, power, temperature and domains overlaid; a rack's elevation; one device's components, ports, sensors and logs |
| **Change the estate** | Add a hall, row or rack from a format; fill a slot with a machine; set a device's fidelity; recable; resize a fabric |
| **Act on it as a technician would** | Power a device off at the PDU, pull a cable, reseat a tray, open a serial console |
| **Break it** | Inject, schedule and clear faults from the packs' catalogues; set random fault rates |
| **Watch the stack respond** | A live event timeline showing every request the software under test made to every device, linked to the fault that caused it |
| **Run and read scenarios** | Start a scenario, follow its steps and assertions, and read the result with its fidelity report |

## Rules

1. **The UI is a client of the control API and nothing else** ([D16](11-decisions.md)). Every
   action has a CLI and API equivalent, and the UI holds no logic the API lacks. If the UI needs
   something, the API grows it first.
2. **Structural changes are estate-file changes** ([D17](11-decisions.md)). Adding a rack in the UI
   produces a diff to the estate file, which is validated, shown and then applied, so the file
   stays the only input ([D1](11-decisions.md)). The UI can write the change back to the file on
   disk, or export it.
3. **Run-time acts are events.** Faults, power, cables and clock control go to the control API and
   into the event log, attributed to the user who made them. They never change the estate file.
4. **The UI shows the hardware side.** It shows what devices report, what the stack *asked of
   them* (by canonical request name), and the stack's state only through accessors the stack
   definition declares, read over the one-way observer path
   ([08](08-scenarios-and-faults.md#what-an-assertion-may-observe), [15](15-security.md)). It never
   reads a stack's database.
5. **No vendor code in the UI.** Rack elevations, device faceplates, fault forms and port
   diagrams are drawn from layout data in rack formats and profiles ([D18](11-decisions.md),
   [04](04-devices-and-racks.md#layout)). A new pack renders without a UI release.
6. **The UI lives in the control namespace** ([D10](11-decisions.md), [15](15-security.md)). It is
   never reachable from a twin network, so the software under test cannot see it, and it is
   authenticated from the first release ([D29](11-decisions.md#d29--security-baseline-from-m0)).
7. **Every screen shows twin health.** A status line carries projection lag and open twin
   incidents, because a result shown while the twin is lagging is not a result
   ([16](16-testing.md#twin-incidents)).
8. **Colour is spent on what needs attention.** Healthy devices are neutral, not green. Severity,
   not vendor, decides colour, and every colour is paired with a shape or label for colour-blind
   users.

## Modes

The console has two modes, so that editing the estate and operating it never get mixed up.

| Mode | What it does | Writes |
|---|---|---|
| **Operate** (default) | See, act, break, watch, run scenarios | Events, through the control API |
| **Design** | Edit a **draft** of the estate: add, remove and move racks and devices, change fidelity, cabling, fabrics and facility; validate; see the diff; apply | The estate file, through `validate` → `diff` → `apply` |

A draft can be edited while the estate runs. Applying it to a running estate has **physical
meaning** ([03](03-estate-model.md#changing-a-running-estate)): a new machine is racked, cabled and
plugged in with its BMC on standby, so the stack under test discovers it the way it would on a
site. A removed machine is powered off and unplugged.

- **Overlays:** health; power (W, and % of feed); inlet and coolant temperature; and domains,
  which outline NVLink domains, NVL36x2 pairs, cooling loops and power feeds.
- **Level of detail.** A hall shows rack tiles with a severity mark; zooming in shows device rows
  inside each tile. It must stay smooth at thousands of racks.
- **Selection is a selector** ([03](03-estate-model.md#paths-and-selectors)). Clicking or
  box-selecting builds one, and the event panel, the fault panel and the CLI all accept it.

```

- **Drawn from the format's layout data**: slots, heights, front and back, and how slot groups
  collapse. An NVL72, an HGX rack and a Helios rack use the same code.
- **The back view** shows cabling: NVLink spine, backend rails, OOB and power feeds.
- Each device shows its **fidelity** (`vm`, `model`, `hardware`) as a badge, because a result on a
  `model` tray means something different from one on a `vm` tray.

### Device

Tabs: **Overview · Components · Ports & cables · Sensors · Firmware · Logs · Interfaces ·
Console · Faults · Fidelity.**

- **Components:** GPUs, CPUs, NICs, DPUs, drives, PSUs and fans, each with health, and the faults
  that apply to it.
- **Ports & cables:** each port, its peer device and port, link state, and LLDP as advertised.
- **Interfaces** is the **protocol inspector**:
  - the device exactly as the stack sees it: a browsable Redfish tree, IPMI sensors and SEL, the
    BMS topics it publishes, its DHCP lease;
  - **every request the stack made to it**, with method, path, status, latency and source address.

  This is how a dialect mismatch or a stack bug is found: "NICo asked for `/Systems/1/Bios`
  and got 404".
- **Console:** serial over LAN for every device; the VM console for `vm` devices.
- **Fidelity:** the profile's `isNot` list and its ledger entries
  ([07](07-fidelity.md#the-fidelity-ledger)).

### Topology

- **Fabrics** are graphs: leaf, spine and rails, laid out by tier, with link state, LLDP
  mismatches and BGP session state as the NOS reports it.
- **NVLink and UALink domains** appear as trays against switch trays, with port state and partitions.
- **InfiniBand** shows partitions and membership as the UFM projection reports them.
- A cable can be pulled from the graph. The cable's two ends are highlighted in the rack back view.

### Facility

- A **power one-line**: feeds → UPS → PDUs and busways → power shelves → racks, with load against
  capacity at each level.
- **Cooling loops**: CDU → racks, with supply and return temperature, flow and alarms.
- **BMS points** as published, in the estate's dialect.

### Faults

```
┌ Inject fault ───────────────────────────────────────────────────────────┐
│ target   a03/compute-tray-07/gpu-2                     (1 component)    │
│ fault    nvidia/xid ▾   xid-79 — GPU has fallen off the bus ▾           │
│ effects  health → Critical · power → 0 W · 18 NVLink ports → down       │
│          kernel log "NVRM: Xid (PCI:…): 79 …" · shim: fallen-off-bus    │
│          Redfish LogEntry (Critical)                                    │
│ when     (•) now   ( ) in [ 30 ] s   ( ) every [   ] (random, seeded)   │
│ clears   on AC cycle   [ ] clear automatically after [   ] s            │
│                                                   [Cancel]  [Inject]    │
└─────────────────────────────────────────────────────────────────────────┘
```

- The catalogue is **filtered to the selection**: only faults whose targets match the selected
  devices and components are offered.
- **Effects are previewed** from the catalogue before injecting, so the user sees what the
  hardware will show.
- **Active faults** are listed, with what they cause and who injected them, and each can be
  cleared individually.
- **Technician acts** sit beside faults: power at the PDU or shelf, reseat, cable pull and
  replace, BMC reset.
- **Chaos:** random fault rates per device class, drawn from the estate's seed.

### Events

- The **live event log** (requests, state changes, faults, observations), filtered by selector,
  kind, source (stack, user, scenario, twin behaviour) and severity.
- **Cause chains.** A fault expands into its effects and then into the stack's requests that
  followed. "What did the stack do about this?" is one click.
- **Clock.** Under the virtual clock (twin-only estates): pause, step, advance, speed. Under the
  wall clock: live only, with a scrub-back over recorded history.
- **Save as scenario.** The faults and acts of a session, with their timing, export as a scenario
  file the user then adds assertions to ([08](08-scenarios-and-faults.md#scenarios)).

### Scenarios and stacks

- Scenarios: list, run, and follow each step and assertion live. The result (`passed`, `failed`,
  `not-run`, `impersonated`) always shows its **fidelity report** ([D11](11-decisions.md)).
- Stacks: what is installed; what each component was handed (addresses, endpoints, as a site
  would hand them); and `dctwin check` as a table of capabilities that are met, met at reduced
  fidelity, stubbed or missing ([06](06-packs-and-stacks.md#the-capability-contract)).

│                                                                                    │
│  row b  ┌────┐┌────┐┌────┐ ┌────┐                                                  │
│         │b01 ││b02 ││b03 │ │b04+│ ← generic/hgx-8gpu · servers 4 · oem/dell/xe9680 │
│         └────┘└────┘└────┘ └────┘                                                  │
├────────────────────────────────────────────────────────────────────────────────────┤
│ diff                                                                               │
│ + sites[site-1].halls[hall-a].rows[b].racks[b04]:                                  │
│     { format: generic/hgx-8gpu,                                                    │
│       params: { server: oem/dell/xe9680-h100, servers: 4 } }                       │
│ + fidelity.overrides: { select: hall-a/b04/server-01, level: vm }                  │
│ validate  ✓ schema  ✓ packs  ✓ cabling (frontend +2 leaves)  ⚠ feed A at 86 %      │
└────────────────────────────────────────────────────────────────────────────────────┘
```

- **Add a rack:** drag a format onto an empty position; a form built from the format's declared
  parameters and ranges appears ([04](04-devices-and-racks.md#rack-formats)).
- **Fill a slot:** clicking an empty slot offers only the profiles that fit it.
- **Fidelity:** set per device or by selector, showing the cost in RAM and CPU against the host's
  capacity ([09](09-runtime.md#sizing)).
- **Fabrics and facility:** change a template's parameters and preview the generated switches and
  cables before applying.
- **Validation runs live** on every change ([03](03-estate-model.md#validation)), and so does the
  stack's capability check.
- **Apply** shows what will physically happen (racked, cabled, powered, VMs created) and whether
  each change is **hot** or **cold**; cold changes (a NOS restart) are refused unless the designer
  confirms them ([03](03-estate-model.md#changing-a-running-estate)). Then it streams the steps.
- **Hall picker.** An estate has one site in v1alpha1 ([D30](11-decisions.md#d30--one-site-per-estate-in-v1alpha1));
  the floor shows one hall at a time with a picker when there are several.

## Users and access

- **By default, a single local user**, with the console on the control address behind the
  per-estate token ([15](15-security.md#users-and-the-control-api)).
- **Shared twins** use OIDC with three roles:
  - `viewer` (see everything);
  - `operator` (run-time acts, faults, scenarios);
  - `designer` (also drafts and applies estate changes).
- Every act is attributed in the event log.
- Many viewers can watch one estate live. Each draft belongs to its author and carries the
  estate file's **etag**; applying it to an estate someone else changed requires a rebase, which
  merges by key (racks by `name`, overrides by `select`, cabling by port ref) and refuses a
  conflict ([03](03-estate-model.md#changing-a-running-estate)).

## Implementation

| Concern | Choice |
|---|---|
| Delivery | A static web bundle embedded in the `dctwin` binary and served by the engine on the control address: one binary, nothing to install separately |
| Framework | React and TypeScript, built with Vite |
| API client | Generated from the control API's OpenAPI description; the UI calls only published operations |
| Live data | The control API's event stream (server-sent events), filtered on the server by selector, so a hall-sized estate does not flood the browser |
| Floor plan | Canvas or WebGL with level-of-detail, so thousands of racks stay smooth ([Q14](11-decisions.md)) |
| Rack and device views | SVG, from layout data |
| Topology | A graph library with layered layout ([Q14](11-decisions.md)) |
| Theming | Severity tokens resolved in one place; light and dark; nominal is neutral |
| Air-gapped use | Fonts and assets are bundled; the UI makes no external requests |
