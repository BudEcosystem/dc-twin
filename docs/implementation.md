# Implementation status

What is built against the [specification](spec/README.md), how it was verified, and what is not
built. Written 2026-10-18 with the first implementation; the spec changes it forced are recorded
as decisions D33–D47 in [11](spec/11-decisions.md) and as additions in [13](spec/13-schemas.md).

## Running it

```bash
make build                         # bin/dctwin and bin/refstack
bin/dctwin assets fetch            # captured BMC trees the vendor dialects bind (MIT, libredfish @ a51ffb1), the os: twin guest image, and NMX-C's interface definition (NVIDIA proprietary, NICo @ 02b92f1; obtained, never committed)
bin/dctwin up examples/estates/gb300-vm.yaml --adapters redfish,ipmi,vm   # one GB300 tray as a real VM (needs QEMU); `dctwin console a01/compute-tray-01`
bin/dctwin validate examples/estates/lab-model.yaml
bin/dctwin up examples/estates/lab-model.yaml --adapters redfish,dhcp,bms,snmp,ipmi,ufm,nvue,nmxc,rms
bin/dctwin status
bin/dctwin fault inject 'a01/compute-tray-07/gpu-2' nvidia/xid/xid-79
bin/dctwin events --select 'a01/**' --no-reads
bin/dctwin scenario run examples/scenarios/twin/xid-and-switch-tray.yaml
bin/dctwin report
bin/dctwin down
make test                          # every test, including the end-to-end scenario suites
scripts/linux-substrate-e2e.sh     # the TAP substrate and a real NOS, in privileged Linux containers (Docker)
```

`dctwin up` prints the control API address (loopback, token in the state directory's
`control.json`) and the **site gateway**: an HTTP CONNECT proxy through which software under test
reaches a BMC at its leased site address (`https://10.30.2.27`) or its host name, and the stack's
own services at the site addresses its outputs name (`siteServices`), as a `vm` guest reaches
them through its segment gateway. `dctwin
credentials` and `dctwin endpoints` print what an operator would hand a stack.

## The reference stack

`cmd/refstack` exists so scenarios can run end to end against software that reaches the twin only
through datacenter protocols. It is a small lifecycle and health manager: its own DHCP server
(relayed requests only), Redfish discovery with gofish through the site gateway, NICo's identity
string rules for hardware types, the leak policies NICo documents, a DSX Exchange consumer on its
own broker, and accessors. **It is not NICo**, and a pass against it says nothing about NICo; it
says the twin presents a datacenter that protocol-level software can discover, read and act on.
The same scenario files run against NICo by mapping the accessor aliases (`machine:
nico.machine`).

## Findings that changed the spec

1. **LeakDetector `DetectorState` is a DMTF `Resource.Health` value** (`OK`, `Warning`,
   `Critical`). The earlier scenario expected `Leak`, which no Redfish service returns; the
   scenario now expects `Critical`.
2. **NICo's current DSX Exchange consumer reads an older message shape than the AsyncAPI**
   (point types `LeakDetectRack`…, `rackName`/`rackID`, timestamps in seconds). The publisher
   follows the AsyncAPI and offers an opt-in `nico-legacy` mirror (D40). **nico-api's own
   integration reads a third** (`integration` on every metadata message, `rackName`/`rackId` on
   the isolation requests, `quality` the string `"1"`), so it never learned where to request a
   rack's isolation; an opt-in `nico-api` mirror publishes the request metadata in that shape on
   topics of its own and takes nico-api's requests there (D40, amended).
3. **libredfish requests `$expand`** for collections, and some captured BMCs answer writes with
   job `Location` headers; both are now served (`$expand`, replayed captured write responses).
   **Ironic writes to settings objects** (`@Redfish.Settings`): XCC's `/Bios/Pending`, iLO's
   lowercase `/bios/settings/`, and on GB trays the system's own `/Settings` for boot overrides;
   iLO resolves URIs case-insensitively. All are now bound, and settings objects that mirror
   every attribute show the applied values after a reset.
4. **The captured BMCs' admin account is `root`** on every vendor capture, so dialect factory
   users follow the capture, not the vendor's documented default.
5. **YAML 1.1 reads `on:` as `true`**, which breaks every `clears.on` and `event.on` written as
   the spec writes them; files are read with YAML 1.2 semantics (D33).
6. **Kea drops relayed packets with an empty relay-source-port sub-option**, so the twin relay
   carries its port (RFC 8357).
7. **Only some dialects declare an IPMI manufacturer id and DHCP vendor class**; the others leak
   `0` and `dc-twin`, which the reports print. Pack follow-up. The BlueField dialect now sends
   `NVIDIA/BF/BMC`, the value NICo's DHCP recognises (`crates/dhcp-common`) and its DPU simulator
   sends, and iDRAC and iLO send `iDRAC` and `CPQRIB3`, the x86 BMC classes it recognises; the
   rest (power shelves, the NVSwitch tray's BMC, Lenovo, Supermicro) remain.
8. **NMX-C's interface definition is NVIDIA proprietary** (`nmx_c.proto`,
   `LicenseRef-NvidiaProprietary`, in NICo's `crates/rpc/proto`), so it is a pack asset obtained at
   a pinned commit (`assets[].obtain.files`, 13) and compiled at run time; neither the file nor
   generated code is committed (D13). The RMS protos are Apache-2.0, so their Go bindings are
   generated and committed with a NOTICE.
9. **Q8, what NMX-C's Subscribe carries**: the twin's answer is change notifications, not
   samples: `HealthStateChanged` (the message carries only a header, so a client re-reads GPUs and
   switches), `FmEvent` topology, control-plane and partition changes, other clients' partition
   responses, and `DomainStateInfo` heartbeats at the client's `heart_beat_rate`. NICo's
   `libnmxc` exposes no Subscribe in its `Nmxc` trait; its generated client does.
10. **Switching a power shelf or PDU off did not change what its rack input delivers** until
    another event recomputed rack power; the engine now recomputes when a source's own power
    changes, so an RMS cold reboot (shelves off, discharge, shelves on) takes and restores the
    trays' power.
11. **NICo pins `librms` at nv-rms-client `v0.10.1` (4bbd502)**; the twin's bindings and the
    harness use 966d7a7, which serves the same RPCs NICo calls. RMS elects "the switch at the
    lowest position in the rack" when no primary is requested; the twin reads that as the lowest
    rack unit (EIA), which on an NVL72 rack is the last switch tray by name.
12. **SONiC-VS is published for x86_64 only**, so an arm64 host could run no real NOS; the twin
    ran SONiC's routing suite and relay without SONiC (`generic/frr-dhcrelay`) and said so (D44).
    It now runs SONiC-VS itself on such a host under the Docker host's binary translation for amd64
    (Rosetta, in colima's VM), unmodified (D44, amended).
13. **ISC dhcrelay, unpatched, sends the receiving interface as its circuit id**: on a VLAN that
    is the VLAN (`Vlan1000`), the same for every BMC of a rack, where SONiC's patched build sends
    `hostname:port`. It also opens a packet socket on every bridge member and discards what arrives
    there ("no IPv4 address assigned"). A stack keying on the per-port circuit id needs SONiC's
    patches (D44).
14. **A veth cannot lose carrier without an admin-down, and that ends a packet socket's reader**
    (`ENETDOWN`); **gVisor's reader for a TAP stops at the first frame for another MAC**, which a
    bridge sends every port as soon as it forgets a MAC (a pulled cable). Endpoints are TAPs whose
    device is the switch port, a cable is the TAP's carrier, and each TAP filters unicast to its NIC's
    MAC in the kernel as NIC hardware does (D45, superseding D20's veth).
15. **A BGP session is Established before its routes are in the kernel**: the first DHCP requests
    a leaf relayed got `Network is unreachable`. `up` waits for every relaying switch to have a route
    to its server.
16. **SONiC-VS needs whatever is cabled to it to checksum its own frames**: SAI's virtual switch
    copies frames between a front-panel port (the container's `eth<n>`) and its host interface with
    a packet socket, which hands over a frame whose checksum the sender left to offload unfilled,
    and SONiC's kernel then dropped Kea's replies (`bad udp cksum`) before its relay saw them. The
    twin turns transmit checksum offload off on the veths it cables to a SONiC-VS port, as SONiC's
    own test harness does on the hosts it attaches (D44).
17. **docker-sonic-vs carries neither a bgp container nor a dhcp_relay one**: its start.sh starts
    zebra and staticd but not bgpd, and no bgpcfgd renders BGP_NEIGHBOR, so the twin writes bgpd's
    configuration and starts it; SONiC publishes its dhcp_relay image only as a build artifact,
    which the twin runs beside each switch in its network namespace with its CONFIG_DB, and which
    renders `dhcrelay -d -m discard -a %h:%p %P --name-alias-map-file … -id Vlan1000 -iu Ethernet48
    10.90.0.10` itself. SONiC's `%p` is the alias of the port the client's MAC is learned on
    (`bridge fdb show`), so the alias is the model's port name. Podman, unlike Docker, does not give
    a container in another's network namespace that container's hostname, which the relay sends as
    `%h`: the runtime joins its UTS namespace too.
18. **A SONiC-VS port has a link only once SONiC has booted**, minutes after the twin cabled it: a
    server attached to it that starts sooner (the test's Kea) finds its interface not running, opens
    no socket and never retries (`DHCPSRV_OPEN_SOCKET_FAIL`); the test's Kea waits for its link, as
    a server cabled to a booting switch would. Natively on x86_64 two switches booted and
    converged in 37 s; emulated on an aarch64 host they took 1.6 minutes with the host quiet and
    over 10 under a load average near 100, every `supervisorctl start` in SONiC's start.sh being
    an emulated Python process (`up` allows a SONiC switch 30 minutes).
19. **Power-on, POST and IPMI timing were wrong for remediation tools** (found by medik8s's Node
    Healthcheck and Fence Agents Remediation, `compat/medik8s`). A power-on from Off did not fire
    `device.reset`, so a fence agent's off-and-on reboot left reset-cleared faults (Xid 48) in
    place; it now does, as a cold boot resets every device. Hosts booted the instant chassis power
    was On, though every profile declares `boot.postSeconds`: the engine now runs POST (scaled)
    before the OS boots, Redfish BootProgress shows it, and a Node is Ready only after it. IPMI
    read chassis power off through the whole power-on window, where a BMC reads its rails on at
    once: it now reads on from PoweringOn.
20. **Restarts, read attribution and fault ids** (found by Metal³ and MAAS, `compat/metal3`,
    `compat/maas`). A warm restart (`ForceRestart`, `GracefulRestart`, IPMI reset) passed through
    Off, so MAAS's power driver read the host off a second later and reset it again; it now keeps
    the host On while it resets, applies pending settings and runs POST, and only a power cycle
    passes through Off. Redfish reads were logged without the authenticated user; they now carry
    it. `fault clear <id>` cleared faults whose ids began with the given one; an id now names one
    fault. The HPE profile had no BIOS version; BiosVersion and the manager's FirmwareVersion now
    follow the model on every dialect. IPMI boot option parameter 3 (Ironic's
    `raw 0x00 0x08 0x03 0x08`) was refused, failing every Ironic boot change over IPMI; it is now
    accepted and read back.

21. **A fault's kernel line must reach the journal as the driver's, and the guest has no vsock**
    (found by NVSentinel, `compat/nvsentinel`; D50). The kernel marks a line written through
    `/dev/kmsg` facility `user`, and journald then reads the driver's `NVRM:` as a syslog identifier
    and strips it, so NVSentinel's Xid pattern would never match; the twin's guest has no journald
    at all. The in-host agent now carries the guest's kernel log out record by record and enters it
    as journald would, and a fault's line is printk'd by the agent's kernel module (`dctwin-kmsg`,
    built for the guest image's kernel), so the record has facility `kern` and nothing needs marking;
    only where the module is absent is the line written through `/dev/kmsg`, entered as the driver's
    printk and marked `DCTWIN_FAULT`. QEMU on macOS has
    no vsock device, so the agent speaks on the guest's serial console, base64-encoding records
    because the vm adapter's boot observer reads the same console. The twin's Xid lines carry the PCI
    function (`PCI:0000:38:00.0`), which the driver omits; NVSentinel accepts it, Fleet
    Intelligence's pattern would not (`compat/fleet-intelligence`). The catalogue now writes the
    driver's two lines (`NVRM: GPU at PCI:0000:38:00: GPU-<uuid>`, then the Xid without the
    function), which fleetint 1.5.0 reads and attributes to the twin's GPU.

22. **A Mokka override document cleared behind the twin stayed cleared** (found by Fleet
    Intelligence's harness, `compat/fleet-intelligence`). Mokka's node agent clears the override
    document whenever it starts; the Mokka sync's resync re-applied only documents that had changed
    since its own last write, so after a node agent restart a GPU the model held lost answered in
    NVML until the model next changed. The resync now applies every host's document again
    (`internal/mokka`, `TestSyncerRestoresADocumentReplacedBehindIt`).
